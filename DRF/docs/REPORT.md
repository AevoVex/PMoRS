# Отчёт по DRF.pdf и DRF2.pdf

Продолжение [DRF2.pdf](../../DRF2.pdf) выполнено в существующем проекте Yatube. Новых заданий для Kittygram в нём нет; его функциональность из первой части сохранена и повторно проверена. [Первоначальный отчёт](REPORT_DRF1.md) сохранён как история выполненной работы.

## Что изменилось в Yatube

| Первая часть | Продолжение: текущий API |
|---|---|
| Последнее упражнение на view-функциях | `PostViewSet`, `CommentViewSet`, `GroupViewSet` |
| API-код находился в posts | Отдельное приложение `api`; posts отвечает за модели и админку |
| Автор возвращался числовым id | Автор возвращается username через `SlugRelatedField` |
| Группа задавалась slug | Группа задаётся и возвращается числовым id |
| Дополнительное `character_quantity` | Поля по примеру DRF2: id, text, author, image, group, pub_date |
| Группы можно было получить списком | Добавлено чтение отдельной группы |
| Комментариев не было | Полный CRUD комментариев по вложенным адресам |

Это последовательные учебные задания с разными контрактами. Текущий `/api/v1/` соответствует DRF2. Решение первой части перенесено в `yatube/lessons` и запускается отдельно, поэтому прежние задания и их тесты не потеряны.

## Как реализовано

Создано приложение [api](../yatube/api). В нём находятся сериализаторы, права доступа, вьюсеты и маршруты текущего API. Конфигурация проекта размещена в `yatube_api`, как в чек-листе; старые импорты `config.settings` оставлены совместимыми с ранее выданными командами.

В [posts/models.py](../yatube/posts/models.py) добавлена модель Comment: текст, автор, пост и дата создания. Связь `post` использует `related_name='comments'`; при удалении публикации её комментарии удаляются каскадно. Поле даты индексировано. Все три модели зарегистрированы в админке. Изменение схемы оформлено новой миграцией `0002_comment`; прежняя миграция и существующие данные сохраняются.

`PostViewSet` и `CommentViewSet` наследуют полный CRUD через общий `AuthorContentViewSet(ModelViewSet)`. `GroupViewSet` наследует `ReadOnlyModelViewSet`: запрет записи обеспечивается возможностями класса, а не отсутствующими вручную маршрутами. Изменить группу через API не может и суперпользователь; для управления справочником существует админка.

В обоих сериализаторах контента явно описано только нестандартное поле автора: `SlugRelatedField(slug_field='username', read_only=True)`. Остальные поля DRF выводит из моделей. Для комментария `post` указан в `Meta.read_only_fields`, поэтому клиент не может перенести комментарий к другой публикации через JSON.

Маршруты организованы в три уровня:

1. `yatube_api/urls.py` подключает только префикс `api/`.
2. `api/urls.py` добавляет `v1/` и отдельный адрес получения токена.
3. `router_v1.register()` описывает ресурсы `posts`, `groups` и `posts/(?P<post_id>\d+)/comments` с явными basename.

Обычный `TokenAuthentication` сохранён. Вход обязателен для всех данных. При создании автор назначается из `request.user`; данные клиента не могут его подменить. `IsAuthorOrReadOnly` разрешает изменение и удаление только автору конкретного объекта. Автор поста не получает права редактировать комментарий другого человека. Staff/superuser также не обходят это правило через API.

## Почему важна проверка вложенного URL

Адрес `/api/v1/posts/10/comments/7/` означает именно «комментарий 7 к посту 10». Одного поиска комментария по id недостаточно: иначе можно прочитать или изменить его через адрес другого поста.

В `CommentViewSet.get_post()` родитель получается через `get_object_or_404`. Результат кэшируется на время обработки одного запроса. `get_queryset()` использует `post.comments`, поэтому чужая для этого URL запись не попадёт в выборку. `perform_create()` использует того же проверенного родителя. Проверка выполняется после аутентификации, но до обработки тела POST: даже пустой POST к отсутствующему посту вернёт 404, а не создаст данные или вызовет 500.

## Что проверено

- **49 тестов из официального api_yatube** прошли. Тестовые файлы не изменялись; их Git blob-хеши совпадают с исходником.
- **52 собственных и ранее созданных теста**: 22 Yatube, 20 Kittygram и 10 ранних уроков Kittygram. Девять новых проверок посвящены вложенным комментариям, запрету подмены связей, правам автора, каскадному удалению и новому JSON-контракту.
- **Postman CLI: 60 запросов и 88 assertions**, ошибок нет. Использованы оригинальные проверки из коллекции; во временной копии заменён только порт локального сервера.
- HTTP smoke обоих проектов, `check`, отсутствие незаписанных миграций и `pip check`.

Итого **101 Python-тест**; результаты полного итогового прогона — в [протоколе](VERIFICATION.md). Проверки Postman считаются отдельно.

## Как запускать и что сдавать

Основные команды запуска остались прежними: `run.ps1 yatube` и `run.ps1 kittygram`. [README](../README.md) и [описание API Yatube](../yatube/README.md) обновлены. [Сценарий демонстрации](DEMO.md) показывает новый формат группы, автора и работу с комментариями.

Для проверки продолжения есть официальный набор в `yatube/tests`, коллекция в `yatube/postman_collection` и скрипт `scripts/run_postman.py`. Этот скрипт поднимает отдельную временную базу и завершает свой сервер после проверки. Существующую базу он не очищает. Перед запуском pytest установите `requirements-dev.txt`.

Для показа первой части: из папки yatube запустите `manage.py runserver 127.0.0.1:8003 --settings=config.lesson_settings` с `YATUBE_STAGE=functions`. В этой версии сохраняются `group: slug`, числовой автор и `character_quantity`. Номер v1 из условий обоих учебных заданий сохранён; режимы запускаются на разных серверах, а не смешиваются в одном контракте.

Требования: [DRF.pdf](../../DRF.pdf), [DRF2.pdf](../../DRF2.pdf), [таблица соответствия](REQUIREMENTS.md). Страница 14 продолжения дополнительно проверена визуально.

Официальные тесты и коллекция взяты из [yandex-praktikum/api_yatube](https://github.com/yandex-praktikum/api_yatube) на commit `723eec8d3618349e42980d2d69b52605f00128f2`. [Манифест хешей](../yatube/upstream-manifest.json) и [описание происхождения файлов](../yatube/UPSTREAM.md) позволяют проверить источник. При интеграции сверены официальные документы DRF: [related-поля](https://www.django-rest-framework.org/api-guide/relations/), [вьюсеты](https://www.django-rest-framework.org/api-guide/viewsets/), [роутеры](https://www.django-rest-framework.org/api-guide/routers/).

Успех публичных тестов не является результатом закрытой проверки на учебной платформе. Работа в учебную систему не отправлялась, сервер в интернете не разворачивался. Postman выполнялся локально, с отключённой отправкой событий результатов; сообщение CLI о входе относится к облачной публикации и не помешало локальному прогону.

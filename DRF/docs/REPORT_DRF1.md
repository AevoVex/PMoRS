## Что получилось

Созданы два самостоятельных Django-проекта с REST API, миграциями, локальными SQLite-базами, демонстрационными данными и автоматическими проверками. В каталоге `lessons` каждого проекта сохранены промежуточные решения. Они нужны для демонстрации заданий, в которых один подход затем заменяется другим.

Проверено 43 автоматических теста: 13 для Yatube, 20 для итогового Kittygram и 10 для ранних уроков Kittygram. Кроме тестового клиента, оба итоговых приложения проверены через настоящие HTTP-запросы к локальным WSGI-серверам на отдельных временных базах. [Протокол и команды](VERIFICATION.md).

## Yatube

Yatube — API публикаций. Пользователь получает обычный DRF-токен по логину и паролю, затем может читать публикации, создавать свои, изменять и удалять только свои записи.

Созданы модели `Post` и `Group`. В Post хранятся текст, дата публикации, автор, необязательная группа и необязательное изображение. Группа содержит название, уникальный slug и описание. При удалении группы публикация сохраняется, а её группа становится пустой: для этой связи используется `SET_NULL`.

`PostSerializer` преобразует модель в JSON и проверяет входные данные. Группа представлена slug, например `"group": "cats"`; это реализовано через `SlugRelatedField`. Группу можно не передавать или очистить значением `null`. Несуществующий slug вызывает 400. Поле `character_quantity` вычисляется через `SerializerMethodField` как длина сохранённого текста, включая пробелы и переводы строк. Оно не хранится отдельно, поэтому не может устареть после редактирования.

Финальное API написано на view-функциях: именно это прямо требуется на странице 134. `api_posts` обслуживает список и создание, `api_posts_detail` — чтение, замену, частичное изменение и удаление конкретного поста. Функция `api_token_auth` выдаёт токен через стандартный валидатор учётных данных DRF.

Автор берётся из `request.user`, установленного механизмом аутентификации. Переданный клиентом `author` игнорируется, поскольку поле только для чтения. До любого изменения или удаления сравнивается автор публикации с текущим пользователем. Другой пользователь получает 403, а отсутствие действительного токена даёт 401. Администратор через этот API также не получает скрытого исключения из правила авторства.

В `yatube/lessons` сохранены первый сериализатор без `id`, класс `APIPost(APIView)` и `PostViewSet(ModelViewSet)` с роутером. Оба альтернативных режима запускаются через отдельные настройки; адреса заданий остаются `/api/v1/posts/`.

## Kittygram

Kittygram — API котиков и их достижений. В итоговой версии владелец — обычный Django User. Пользователь регистрируется через Djoser, получает пару JWT access/refresh через SimpleJWT и передаёт access-токен в заголовке `Authorization: Bearer ...`.

Основные модели — `Cat`, `Achievement` и промежуточная `AchievementCat`. Один пользователь может иметь несколько котов; один кот может иметь несколько достижений, а одно достижение может относиться к разным котам. Промежуточная таблица хранит эти связи.

Для котов используется `ModelViewSet`: он предоставляет стандартные CRUD-операции. Владелец назначается в `perform_create` из текущего пользователя. `IsOwnerOrReadOnly` разрешает чтение всем вошедшим пользователям, а изменения и удаление — только владельцу. Подмена `owner` в JSON не меняет хозяина.

Достижения передаются вложенным массивом объектов с полем `achievement_name`. Через `source='name'` это внешнее имя связано с внутренним полем модели. Сериализатор переопределяет `create` и `update`: сначала сохраняет кота, затем создаёт или находит достижения и связывает их. Операция выполняется в транзакции. Повторяющиеся названия и связи не размножаются.

Поле `achievements` необязательно. При обновлении отсутствие поля сохраняет текущие связи; пустой массив удаляет связи этого кота, но не сами общие достижения; непустой массив заменяет связи. Это явно выбранная семантика и для PUT, и для PATCH. Она позволяет редактировать кота, не пересылая достижения каждый раз.

Добавлены проверки:

- `birth_year`: строго `текущий год − 40 < год рождения ≤ текущий год`, как в коде задания. Возраст ровно 40 лет уже не принимается.
- `color`: только `Gray`, `Black`, `White`, `Ginger`, `Mixed`.
- `name`: до 16 символов; имя не может совпадать с кодом цвета.
- Пара `name + owner` уникальна: у разных хозяев одно имя допускается, у одного — нет.
- При PATCH проверка имени и цвета дополняет отсутствующее поле значением из существующего объекта.

Уникальность проверяется на двух уровнях. `UniqueTogetherValidator` возвращает понятный ответ 400 до сохранения. `UniqueConstraint` защищает БД, в том числе если два запроса одновременно прошли предварительную проверку. `CurrentUserDefault` делает владельца доступным валидатору до `save`, при этом клиент не получает права менять это поле.

Список котов возвращает только `id`, `name`, `color`, а детальный запрос — все поля, включая возраст и достижения. Дополнительный action `/cats/recent-white-cats/` возвращает пять последних добавленных белых котов. `/mycats/` демонстрирует сборку вьюсета из миксинов: создание и чтение одной записи разрешены, список и изменение запрещены.

Пользователи доступны для чтения через `/users/`. Самостоятельная регистрация и операции со своим аккаунтом идут через `/auth/users/` Djoser. Пароли и email в общем списке пользователей не выдаются.

Общий справочник достижений допускает чтение и добавление вошедшими пользователями; изменение и удаление доступны сотруднику с `is_staff=True`. Это дополнительное решение: изменение общего достижения обычным пользователем иначе затронуло бы котов других владельцев. Сам маршрут остаётся `ModelViewSet`, полный CRUD доступен сотруднику.

## Ранние учебные этапы

В Kittygram отдельный режим `config.lesson_settings` использует `lessons.sqlite3`. Здесь находятся исходные простые модели Cat/Owner, функции, массовое создание, APIView, дженерики, обычный и низкоуровневый вьюсеты, строковые связи владельца и котов, эксперимент с hex-цветами. В раннем режиме можно передать `owner_id`; в ответе `owner` представлен строкой. Это явное дополнение для удобного создания связей после перевода `owner` в read-only строковое поле.

По умолчанию ранние уроки доступны без входа, как в начале PDF. Переменная `KITTYGRAM_LESSON_TOKEN=1` включает промежуточный этап TokenAuthentication. Итоговое приложение всегда использует JWT и проверку владельца. Учебные маршруты не подключены к итоговому API.

## Что исправлено относительно примеров

1. На странице 133 для refresh ошибочно повторён адрес создания токена. Использован настоящий `/auth/jwt/refresh/`. Получение нового access само по себе не отзывает ранее выданный access; прежний действует до истечения срока. Механизм отзыва здесь не заявляется.
2. Для пяти **последних** белых котов задана сортировка `-id`: один только срез `[:5]` из примера не гарантирует последние записи.
3. Валидация объекта учитывает PATCH с одним полем. Прямое обращение `data['name']` из PDF могло бы вызвать KeyError.
4. Для вложенных достижений реализовано не только создание, но и обновление, иначе стандартный `ModelSerializer.update` не обработает такую запись.
5. Временный эксперимент с hex-цветами вынесен отдельно, потому что на странице 97 его предлагают отменить, а финальная модель использует фиксированный список цветов.
6. В раннем примере год может быть `null`; возраст для него также `null`. В финальной версии год обязателен.
7. Точные зависимости из старого примера не копировались вслепую: установлены Django 5.2.18, DRF 3.16.1, Djoser 2.3.5, SimpleJWT 5.5.1. Совместимость конкретной установленной комбинации подтверждена тестами и HTTP-проверкой.

## Почему такая структура

Два отдельных проекта соответствуют двум независимым заданиям и не смешивают обычные токены Yatube с JWT Kittygram. В каждом код разделён по обязанностям: модель отвечает за хранение, сериализатор — за формат и валидацию, view — за обработку запроса, permission — за доступ, URL — за маршрутизацию.

SQLite и автоматическое создание локального ключа уменьшают количество ручных действий при проверке преподавателем. Настоящие миграции позволяют создать базы с нуля. `seed_demo` можно запускать повторно: он не сбрасывает существующие пароли и не создаёт повторные демонстрационные записи. Для моделей со связями применены `select_related` и `prefetch_related`, чтобы не делать отдельный запрос БД на каждую строку ответа.

## Граница результата

Выполнена локальная реализация и проверка API по PDF. В наличии исходники, миграции, инструкции, запросы, тесты и отчёт.
